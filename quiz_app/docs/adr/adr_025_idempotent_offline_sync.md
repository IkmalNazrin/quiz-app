# ADR 025: Idempotent Offline Sync Processing

## Status
Proposed

## Context
As part of our enterprise hardening, we introduced offline caching using Drift (SQLite) to buffer user actions (like `submit-answer`) when the network is degraded. Our initial implementation uses a simple "queue and flush" mechanism: when the device comes back online, it fires all queued mutations to the Supabase Edge Functions.

However, this "last-write-wins" or "dumb flush" approach introduces severe race conditions:
1. **Concurrency Clashes**: If multiple users in the same game session drop offline, submit answers locally, and reconnect simultaneously, the server receives a flood of overlapping state changes. 
2. **Duplicate Mutations**: If a network timeout occurs *after* the server processes the `submit-answer` mutation but *before* the client receives the 200 OK, the client will retry the mutation upon reconnection, potentially resulting deduplication issues or double-scoring.

To achieve true enterprise-scale reliability, our offline sync engine must guarantee **exactly-once processing** on the server, regardless of how many times a client retries a payload.

## Decision
We will upgrade our offline sync architecture to use **Idempotency Keys** combined with a **Server-Side Request Ledger**. 

1. **Client-Side Sourcing**: Every offline-capable mutation generated by the client will be assigned a locally generated UUIDv4 known as the `idempotency_key`. This key is stored in the local Drift database alongside the mutation payload.
2. **Edge Function Validation**: The `game-orchestrator` Edge Function will be updated to accept the `idempotency_key`. 
3. **Database Ledger**: Before processing the mutation, the server will attempt to insert the `idempotency_key` into a newly created `processed_mutations` table. 
   - If the insert succeeds, the server processes the answer and commits the transaction.
   - If the insert fails (due to a unique constraint violation), the server instantly returns a `200 OK` (or `409 Conflict` depending on the desired client behavior), bypassing the core game logic because this mutation was already processed successfully.
4. **Client Cleanup**: Upon receiving any success response (even a deduplicated one), the client aggressively purges the mutation from the local Drift queue.

## Consequences

### Positive
- **Guaranteed Exactly-Once Processing**: Eliminates double-scoring and duplicate actions.
- **Resilience to Poor Networks**: Clients can safely retry timeout requests without fear of corrupting server state.
- **Foundation for CRDTs**: This ledger approach is the first stepping stone towards full Conflict-Free Replicated Data Types natively in the game engine.

### Negative
- **Database Overhead**: Introduces an extra write (to `processed_mutations`) for every critical game action.
- **Latency**: Sub-millisecond impact on Edge Function execution time due to the ledger check. This is an acceptable trade-off for data integrity.

## Next Steps
1. Create the `processed_mutations` table in Supabase via migration.
2. Update the `SyncWorker` and `game-orchestrator` to implement the idempotency handshake.
